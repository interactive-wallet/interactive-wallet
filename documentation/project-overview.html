Project Overview

"Trust is built by showing your work."
— Core design philosophy of the Interactive Wallet

The Interactive Wallet is a Self-Sovereign Identity (SSI) wallet designed around radical transparency. Most SSI wallets treat cryptographic operations as a black box — credentials arrive, proofs are sent, and the user sees only the result. This project challenges that assumption.

The wallet surfaces three layers of transparency to the user:

👀

Before

What is being asked of you. Who is asking, what attributes they need, for what purpose — before you agree to anything.

⚙️

During

What is happening behind the scenes while it happens. Each cryptographic step, DIDComm message, and ledger lookup described in plain language.

📋

After

What was done. A hash-chained, tamper-evident audit log of every operation, persisted and readable at any time.

Research contribution: The project investigates whether surfacing SSI internals in real time increases user comprehension and trust — without overwhelming or alarming them.

The SSI Triangle — Issuer / Holder / Verifier

Self-Sovereign Identity is structured around three roles. Their relationships form what is commonly called the trust triangle.

📱
Holder
The wallet user
← receives credential

Verifier

🏛️ Issuer

Creates and signs verifiable credentials. Registers their DID, schema, and credential definition on the VON ledger. Sends credentials directly to the Holder via DIDComm — not via the blockchain.

📱 Holder

Receives, stores, and presents credentials. The wallet user. Has full control — credentials are stored locally in an encrypted Askar database, not on any server or ledger.

🚗 Verifier

Requests proof from the Holder. Checks the Issuer's credential definition on VON to verify authenticity. Never sees more than what the Holder chooses to disclose (ZKP).

Important: Credentials are never stored on the blockchain. Only the schema (what fields a credential has) and the credential definition (the Issuer's public key for that schema) are on the ledger. The actual credential travels directly Issuer → Holder via encrypted DIDComm.
3

What is VON? (Verifiable Organizations Network)

VON is a local Hyperledger Indy blockchain running in Docker. It acts as the shared trust registry that all three SSI roles can reference.

✅ What VON stores

  • 📌 Decentralized Identifiers (DIDs)
  • 📄 Credential Schemas
  • 🔑 Credential Definitions (public keys)
  • 🔁 Revocation Registries

❌ What VON does NOT store

  • 🚫 Actual credentials
  • 🚫 Personal data
  • 🚫 Proof presentations
🐳

Docker Setup

4 Indy validator nodes + a web browser at localhost:9000. Boots from a genesis.txn file that bootstraps initial DIDs and network trust.

🔍

Trust Registry

Verifiers resolve the Issuer's credential definition from VON to cryptographically verify that a presented credential was signed by a known, registered Issuer.

🌐

Local Only

For development, the VON network is entirely local. In production, this would be replaced by a real Indy network (e.g., Sovrin, IDunion, or a consortium ledger).

What is Credo-TS?

Credo-TS (formerly Aries Framework JavaScript) is a TypeScript implementation of the Hyperledger Aries specification — the standard protocol stack for SSI agents. It handles everything from DID management to encrypted credential exchange.

TypeScript / Node.js Hyperledger Aries DIDComm v2 AnonCreds / ZKP

This project uses four Credo-TS modules:

AskarModule Storage

Encrypted local storage engine. Stores private keys, credential records, and connection state in a SQLite database. Uses the Askar secure enclave — no plaintext secrets on disk.

IndyVdrModule Ledger

Blockchain interaction layer. Reads and writes DIDs, schemas, and credential definitions to/from the Indy ledger (VON). Uses the indy-vdr native library under the hood.

AnonCredsModule ZKP

Privacy-preserving credential format. Enables selective disclosure (share only some attributes) and zero-knowledge proofs (prove a claim without revealing the value — e.g., "I am over 18").

DIDCommModule Comms

Encrypted peer-to-peer messaging. Handles Out-of-Band invitations, connection establishment, and the full Aries credential exchange protocol between agents.

Why Credo-TS? It is the most mature TypeScript SSI agent framework, maintained by the OpenWallet Foundation. It implements all major Aries RFCs and supports both AnonCreds and W3C Verifiable Credentials.

The Two Agents

📱

wallet-agent

The user's personal SSI agent. Runs as a Node.js server alongside the Flutter app.

✦ Stores credentials locally in Askar
✦ Receives credential offers from issuers
✦ Generates and presents proofs to verifiers
✦ REST API on :3000 for frontend
✦ DIDComm on :3001 for agent comm.
🏛️

issuer-agent

Simulates a credential authority (e.g., Führerscheinbehörde). For testing and development only.

✦ Issues Führerschein credentials
✦ POST /setup — register on VON (once)
✦ GET /invitation — DIDComm invite
✦ POST /issue — send credential offer
✦ REST API on :3002, DIDComm :3003
Why two separate agents? In a real deployment, the Issuer agent would be run by the issuing authority (e.g., a government agency), not the wallet user. Separating them lets us test the full Aries protocol stack locally, including the DIDComm connection and credential exchange flow.

DIDComm — How Agents Talk

DIDComm is an encrypted, transport-agnostic messaging protocol for DID-based agents. All messages are encrypted end-to-end using keys derived from the agents' DIDs. Neither the transport layer nor any intermediary can read the content.

End-to-End Encrypted Transport Agnostic DID-based Auth Aries RFC compliant

The Führerschein Flow — End-to-End

This is the complete journey of issuing a test driver's license (Führerschein) credential from scratch.

1
VON Network is running Docker
Four Indy validator nodes are active. The ledger explorer is accessible at localhost:9000. This is the shared trust registry all agents will use.
2
Both agents start Node.js
wallet-agent and issuer-agent start, initialize their Credo-TS agents, connect to VON via genesis.txn, and open their REST + DIDComm ports.
3
One-time setup POST /setup
The Issuer registers its DID on VON as a Trust Anchor, then writes the Führerschein schema and credential definition to the ledger. This only needs to happen once per ledger.
4
Get connection invitation DIDComm
Call GET /invitation on the issuer. Returns an OOB (Out-of-Band) invitation URL containing the Issuer's DIDComm endpoint and public key.
5
Wallet connects DIDComm
POST the invitation URL to wallet's /receive-invitation. The wallet performs the Aries connection protocol — both agents exchange DIDs and establish an encrypted channel.
6
Issue credential offer DIDComm
Call POST /issue on the issuer with the connection ID and Führerschein attributes (Vorname, Nachname, Geburtsdatum, Klasse, Ausstellungsdatum). The Issuer sends a DIDComm credential offer.
7
Wallet auto-accepts and stores Askar
The wallet-agent auto-accepts the credential offer, sends a credential request (blinded link secret), receives the signed AnonCred, and stores it encrypted in Askar. An audit log entry is written.
8
Frontend reads credential GET /credentials
The Flutter app or curl calls GET /credentials on the wallet. The Führerschein appears with all attributes. It is now ready for selective disclosure and ZKP-based proof presentations.

Two Transparency Channels

The core research contribution of this project: making every layer of an SSI interaction visible to the user. Two distinct transparency mechanisms are implemented.

🔍 On-Request Transparency

Shown before the user agrees to a proof request. The wallet surfaces all relevant context so the user can make an informed consent decision.

🏢
Who is asking Verifier's DID, registered name, position in the trust registry
📋
What is being asked for Exact credential attributes requested, displayed in plain language (not attribute IDs)
🎯
Why it's being requested The verifier's stated purpose for each data point
⏱️
Data retention How long the verifier claims they will keep the data

📜 Behind-the-Scenes Log

A persistent audit trail of every operation. Tamper-evident via hash chaining. Readable in plain language at any time.

🔗
Hash-chained entries Each entry links to the previous via SHA-256 hash — any modification breaks the chain
🌐
Layer-boundary logging Every operation crossing a system boundary is logged (DIDComm send/receive, ledger read/write, proof generation)
💬
Plain language descriptions "Resolved DID did:indy:...", "Generated ZKP proof", "Signed with device key", "Received credential offer"
🔒
Tamper evidence "Recorded entry #1247 linked to #1246" — the UI can verify the chain at any time

Future: Watcher + Broker (Phase 4)

🚧 Phase 4 — Not yet implemented

Hyperledger Indy ledgers are pull-based — agents must actively query the ledger to detect changes. There is no push notification mechanism. This creates a fundamental problem for mobile wallets: how does a holder know when their credential has been revoked?

The Problem: Without active polling, a revoked credential continues to appear valid in the user's wallet until the next manual sync. This is unacceptable for high-stakes credentials like driver's licenses or medical certifications.
👁️

Watcher Service

A dedicated service that continuously polls the VON ledger and detects meaningful changes: credential revocations, DID document updates, new schema versions, and key rotations.

📨

RabbitMQ Broker

A hierarchical message broker that routes change notifications only to wallets that hold the affected credentials. Avoids broadcasting all changes to all wallets.

📲

Push Notifications

Mobile wallets receive a wake-up push notification (via APNS/FCM), then connect to their DIDComm mediator to fetch queued messages containing the revocation details.

Setup Instructions

Complete guide to running the full stack locally, from zero to a Führerschein in your wallet.

Prerequisites

Docker + Docker Compose Node.js ≥ 18 pnpm ≥ 9 Flutter SDK (for app) curl or Postman

Step 1 — Start VON Network

# Clone VON network if not already present
git clone https://github.com/bcgov/von-network
cd von-network

# Start the local Indy ledger (4 validator nodes + explorer)
./manage start

# Verify: open the ledger explorer
# http://localhost:9000

Step 2 — Start wallet-agent

cd wallet-agent

# Install dependencies (first time only)
pnpm install

# Start the wallet agent (REST :3000, DIDComm :3001)
pnpm start

# Verify
curl http://localhost:3000/credentials
# → {"credentials": []}

Step 3 — Start issuer-agent

cd issuer-agent

# Install, build, and start
pnpm install
pnpm run build
pnpm start

# REST :3002, DIDComm :3003

Step 4 — One-Time Ledger Setup

# Register Issuer DID on VON + write Führerschein schema + creddef
# Only needed once per fresh VON ledger instance
curl -X POST http://localhost:3002/setup

# Expected: {"success": true, "did": "did:indy:...", "credDefId": "..."}

Step 5 — Create a DIDComm Connection

# 1. Get invitation from issuer
curl http://localhost:3002/invitation
# → {"invitationUrl": "didcomm://...?oob=..."}

# 2. Send invitation URL to wallet
curl -X POST http://localhost:3000/receive-invitation \
  -H "Content-Type: application/json" \
  -d '{"invitationUrl": "didcomm://...?oob=..."}'
# → {"connectionId": "abc-123-...", "state": "completed"}

Step 6 — Issue a Führerschein

curl -X POST http://localhost:3002/issue \
  -H "Content-Type: application/json" \
  -d '{
    "connectionId": "abc-123-...",
    "vorname": "Max",
    "nachname": "Mustermann",
    "geburtsdatum": "1990-01-01",
    "fuehrerscheinklasse": "B",
    "ausstellungsdatum": "2024-01-01"
  }'

# Issuer sends DIDComm credential offer → wallet auto-accepts → stores in Askar

Step 7 — Verify the Credential is Stored

curl http://localhost:3000/credentials

# → {
#     "credentials": [{
#       "id": "cred:...",
#       "schemaId": "Fuehrerschein:1.0",
#       "attributes": {
#         "vorname": "Max",
#         "nachname": "Mustermann",
#         "fuehrerscheinklasse": "B",
#         ...
#       }
#     }]
# }

🎉 Done!

The Führerschein credential is now stored in your encrypted Askar wallet. You can view it in the Flutter app or use GET /credentials. The transparency audit log (GET /log) will show every step that occurred.
